# Descripción del Proyecto LILY-GO

## 1. Visión General
Este proyecto implementa un firmware para dispositivos **LILYGO T-SIM7000G (ESP32)**, diseñado para aplicaciones de telemetría IoT. El sistema es capaz de recolectar datos de sensores, obtener ubicación GPS y transmitirlos a un servidor central a través de redes GPRS o WiFi, utilizando el protocolo MQTT.

## 2. Alcance del Proyecto
El firmware está orientado a la monitorización remota de activos, permitiendo:
- **Geolocalización:** Rastreo de ubicación mediante GNSS (GPS/GLONASS).
- **Telemetría de Sensores:** Lectura de sensores analógicos (ADC), digitales (DS18B20) e industriales (Modbus RTU).
- **Conectividad Híbrida:** Redundancia de comunicación mediante GPRS (celular) y WiFi.
- **Gestión Remota:** Configuración y actualización de firmware (FOTA) de manera remota.
- **Almacenamiento Local:** Buffering de datos en memoria no volátil cuando no hay conectividad.

## 3. Especificaciones Técnicas

### 3.1 Hardware Soportado
- **MCU:** ESP32 (Dual Core, WiFi/BLE).
- **Módem:** SIMCom SIM7000G (LTE CAT-M1 / NB-IoT / GPRS / GNSS).

### 3.2 Funcionalidades Clave

#### Conectividad y Protocolos
- **MQTT:** Protocolo principal para envío de datos y recepción de comandos.
- **Modo Híbrido:** Prioriza la conexión WiFi cuando está disponible; cambia automáticamente a GPRS en caso contrario.
- **Sincronización Horaria UTC (`ClockSync`):** Sincronización no bloqueante en GSM mediante `+CNTP` modo 1 (UTC puro vía URC), respaldo de red `*PSUTTZ` y fix GPS, además de NTP estándar cuando opera por WiFi.
- **Keep Alive Configurable:** Trama de diagnóstico con intervalo persistente en Flash configurable mediante `DVL+SKA=<seg>` y `DVL+QKA` (`900 s` por defecto).
- **Diagnóstico WiFi por Serial:** Al conectarse o reconectarse, informa ID LILY, SSID/BSSID, MAC, hostname, IP, máscara, gateway, DNS, canal, RSSI y destino MQTT sin exponer la contraseña.
- **Buffering (Flash):** Almacenamiento temporal de paquetes en memoria SPIFFS/LittleFS ante cortes de conexión para evitar pérdida de datos.

#### Sensores e Interfaces
- **ADC (Analógico):**
  - Lectura de 2 canales analógicos: GPIO34 y GPIO39.
  - Configuración de filtros (umbral mínimo), factores de calibración (pendiente/offset) y alisado (promedio móvil).
- **Modbus RTU (RS485):**
  - Maestro Modbus para interrogar dispositivos esclavos industriales.
  - Hasta 25 consultas configurables por idx (ID del dispositivo, Función, Dirección y Cantidad), ejecutadas de una en una cada 2 segundos como mínimo, con 200 ms de espera por respuesta.
  - Cada consulta publica también al recibir su primera respuesta válida o cuando cambian sus bytes de datos (datos_hexa) respecto de la última respuesta válida de ese idx. Una respuesta igual actualiza date_respuesta sin disparar otro envío; timeout, trama inválida o excepción no disparan el evento. Se conserva el mismo JSON y topic por idx. La publicación periódica por DVL+STIME y el keep-alive siguen independientes. Si el evento no puede publicarse, se intenta encolar en la flash existente, con su límite de 511 bytes por mensaje y su capacidad finita; los paquetes más antiguos pueden sobrescribirse al llenarse la cola. El evento se procesa antes de la siguiente consulta, sin esperar STIME. No se agregan comandos ni se cambia el orden de los datos.
  - Publicación MQTT independiente por idx de consulta, incluso si varias consultan al mismo dispositivo o son idénticas.
  - Campos `consulta`, `respuesta`, `datos_hexa` y `date_respuesta`: TX completa, última RX válida, datos compactos sin cabecera ni CRC y fecha UTC de recepción. `date` indica cuándo se armó el mensaje. La conversión de los bytes corresponde a la plataforma.
  - Ante una consulta fallida conserva la última lectura válida. Lecturas y fechas están en RAM; se limpian al reiniciar, reconfigurar o borrar la consulta y al cambiar baud/paridad, sin borrar los mensajes históricos en flash.
  - Paridad persistente NONE/EVEN/ODD mediante `DVL+SPARITY_MODBUS` y `DVL+QPARITY_MODBUS`; baud compartido mediante `DVL+SBAUD` y `DVL+QBAUD`. Cambiar uno conserva el otro. Serial común usa 8N1; Modbus usa el formato guardado (8N1/8E1/8O1).
- **Sensores Dedicados:** Soporte nativo para sensor de temperatura DS18B20.
- **Sensores BLE MOKO:** H4 Pro valida el nombre `DVL` o `PaPeR` por MAC durante el escaneo y publica solo la ultima trama `0x70` de temperatura/humedad; los otros slots no generan un JSON que la desplace. MOKO Door se decodifica de forma independiente. L02S/EA01 publica el estado de puerta en `door` y `door_open` cuando es detectado. La telemetría de alimentación publica la lectura `SOLAR_IN` como tensión principal y usa `4.208701 V` simulado para backup cuando la principal supera `4.5 V`.
- **Expansora I/O:** Comunicación con placas expansoras vía puerto serial secundario.
- **Motor de Eventos Programable (Micro-PLC):** Evaluación periódica cada 100 ms de 4 reglas (`EV0`..`EV3`) con temporizador TON y rearme (`ONESHOT`/`REPEAT`). Monitorea tensiones/ADC (`VPRIN`, `VBACK`, `ADC0`, `ADC1`), entradas digitales/enlace (`DI1`, `DI2`, `COMM`), sensores cableados (`TEMP`, `S0`..`S15`), balizas BLE Moko filtrables por MAC (`BLE_DOOR`, `BLE_MOV`, `BLE_TEMP`, `BLE_HUM`, `BLE_BAT`), salud del ESP32 (`TEMP_MCU`, `HEAP`, `BTN`) y 4 disparadores fecha/hora (`DT0`..`DT3`). Ejecuta acciones locales (`OUT`, `CYCLE_PWR`, `RESTART`) y emite alertas inmediatas por MQTT.

#### Gestión del Dispositivo
- **Modo AP (Access Point):** Servidor web integrado para configuración inicial (WiFi, parámetros MQTT) activable mediante botón físico.
- **Comandos Seriales/Remotos:** Interfaz de línea de comandos (CLI) para configuración en tiempo real (ver `main/COMANDOS.md` y `comandos.txt`).
- **FOTA:** Actualización de firmware vía HTTP.
- **Watchdog:** Mecanismos de reinicio automático ante fallos de software o módem.

## 4. Arquitectura de Datos
El sistema reporta datos en formato JSON a través de tópicos MQTT específicos:
- `DVL/LILY-GO/<ID_LILY>`: Tópico principal de telemetría.
- `DVL/LILY-GO/<ID_LILY>/ADC`: Reportes específicos de entradas analógicas.
- `DVL/LILY-GO/<ID_LILY>/MODBUS/<idx>`: Reportes Modbus separados por consulta (idx 1-25), con `baud` y `paridad`. El ID del dispositivo está en el primer byte de la trama `consulta`.
- `DVL/LILY-GO/<ID_LILY>/EVENTOS`: Alertas inmediatas generadas por el Motor de Eventos (Micro-PLC).

Los paquetes incluyen timestamp, ubicación, e información de sensores según la configuración habilitada (`EN_SENSOR`, `EN_SERIAL`, `EN_MODBUS`).
